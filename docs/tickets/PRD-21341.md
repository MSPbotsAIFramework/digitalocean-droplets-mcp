## Product design

### Goals / Non-goals

- Goal: an MSPbots-hosted MCP server that lets any MCP-compatible agent list, inspect, create, and destroy DigitalOcean Droplets, and drive their lifecycle (power/reboot/resize/snapshot/restore/backup toggles), scoped to whichever DigitalOcean account's API token is supplied on the request.
- Goal: expose the reference data (regions, sizes, images) an agent needs to pick valid values before creating a Droplet, so `create_droplet` calls do not fail on guessed slugs.
- Goal: every destructive action (delete Droplet, delete snapshot, any Droplet action) requires an explicit resource id from the caller — no bulk, wildcard, or "all droplets" destructive operation.
- Non-goal: DigitalOcean resources outside Droplets (Databases, Spaces, Kubernetes, Load Balancers, Firewalls, VPCs, Domains, Projects, Monitoring/Alerts, Billing). PRD-21339 (Databases) is a separate connector; others are out of scope until a ticket asks for them.
- Non-goal: OAuth or multi-account credential management. DigitalOcean's own API only supports personal-access-token bearer auth for this use case; the connector follows the same single-header credential pattern already used by the platform's other API-key-style connectors.
- Non-goal: a DigitalOcean account UI or any change to `agent.mspbots.ai` — this ticket delivers a backend MCP connector only; the existing generic "Connector" form (credential-style variant) is reused unchanged.
- Non-goal: changes to `mcp-service-gateway` or any control-plane repo. Nothing in this ticket touches routing, vendor registration mechanics, or OAuth — see Decisions below.

### Acceptance criteria AC1..AC13

- AC1: Given a valid `X-DigitalOcean-Api-Token`, when the agent calls the list-droplets tool, then it returns every Droplet on that account; an account with zero Droplets returns an empty list, not an error.
- AC2: Given a Droplet id that exists on the account, when the agent calls the get-droplet tool, then it returns the full Droplet record (id, name, status, region, size, image, networks); given an id that does not exist, it returns a `not_found` error envelope, not a 500 or an unhandled exception.
- AC3: Given name, region, size, and image (slug or numeric id), when the agent calls the create-droplet tool, then a new Droplet is created and the tool returns its id and initial status; given a missing required field, the tool rejects the call with `invalid_argument` before any call reaches the DigitalOcean API.
- AC4: Given an explicit Droplet id, when the agent calls the delete-droplet tool, then only that Droplet is destroyed; the tool has no parameter that destroys more than one Droplet per call, and a non-existent id returns `not_found`.
- AC5: Given a Droplet id and one supported action type (power_on, power_off, power_cycle, shutdown, reboot, resize, rename, snapshot, restore, enable_backups, disable_backups, enable_ipv6), when the agent calls the droplet-action tool, then exactly that action is performed on that Droplet and the tool returns the action's id and initial status; an unsupported action type is rejected with `invalid_argument` before calling the DigitalOcean API.
- AC6: Given an action id returned by AC5, when the agent calls the list-droplet-actions or get-action tool, then it can observe the action's status transition from `in-progress` to `completed` or `errored`.
- AC7: Given a Droplet id, when the agent calls the list-snapshots or list-backups tool, then it returns that Droplet's snapshots/backups; given an explicit snapshot id, the delete-snapshot tool destroys only that snapshot (no bulk delete).
- AC8: When the agent calls the list-regions, list-sizes, or list-images tool, then it returns the slugs/ids needed to populate a create-droplet call, each respecting a `limit` parameter (default ≤ 50, hard cap ≤ 200) and returning `has_more` instead of an unbounded list.
- AC9: Given a request with no `X-DigitalOcean-Api-Token` header, when any tool is called, then the server returns 401 with a body listing the required header, before any call reaches the DigitalOcean API.
- AC10: Given the DigitalOcean API returns 401/422/429/5xx or a network failure, when a tool call is in flight, then the server maps it to `unauthorized`/`invalid_argument`/`rate_limited` (relaying `Retry-After`)/`upstream_error` respectively, inside the structured error envelope — never an unhandled exception or a raw 500.
- AC11: Given two concurrent requests carrying two different tenants' `X-DigitalOcean-Api-Token` values, when both call any tool at the same time, then neither request's response, log entry, or outbound call ever carries the other tenant's token or data (request-scoped credential isolation, no shared/global state).
- AC12: Given the server has no DigitalOcean credential available and no network path to `api.digitalocean.com`, when `GET /health` is called, then it still returns 200 (the health check is a local liveness probe, not a DigitalOcean reachability check).
- AC13: Given a fresh connection with no prior session, when the agent calls `initialize` followed by `tools/list`, then both succeed without requiring session affinity (stateless Streamable HTTP), and `tools/list` returns a non-empty tool list.

## Tech design

### Conclusion

Build a new Python 3.12 + `uv` + FastMCP service in `MSPbotsAIFramework/digitalocean-droplets-mcp` (currently an empty scaffold), following the vendor-mcp-development SOP structure byte-for-byte (same shape as every other `<vendor>-mcp` repo in the org — no repo to copy from directly since this is the first commit, but the contract, container, and test layout are identical across the org's existing connectors). The service is a thin, stateless HTTP wrapper around DigitalOcean's public REST API v2 (`https://api.digitalocean.com/v2`), reading a single bearer token from a request header and mapping DigitalOcean's Droplets/Droplet Actions/Snapshots/Backups/Regions/Sizes/Images endpoints onto 13 MCP tools. No gateway or control-plane change is needed — DigitalOcean's API has no remote-MCP or OAuth requirement for this use case.

### Where the current implementation lives

Nothing exists yet. `README.md:1-2` is the only file in the repo (`7099212`). There is no prior DigitalOcean code in `MSPbotsAIFramework` to reuse. The nearest same-shape reference is the SOP itself (`~/.claude/skills/vendor-mcp-development/reference/vendor-mcp-development-sop.md`) and its skeleton in `SKILL.md` §A3 (FastMCP, Streamable HTTP, `contextvars` credential isolation, structured error envelope) — this design follows that skeleton exactly, it is not a new pattern.

### Data & API contract

Base URL: `https://api.digitalocean.com/v2`. Credential header: `X-DigitalOcean-Api-Token` (the connector maps it internally to DigitalOcean's own `Authorization: Bearer <token>` convention; the custom header name keeps this connector consistent with every other MSPbots connector's "vendor-prefixed custom header" pattern, per SOP §3.1 — it does not change what DigitalOcean itself requires).

Tool table (13 tools, all prefixed `digitalocean_droplet_`/`digitalocean_` to avoid cross-service name collisions, e.g. with a future `digitalocean-databases-mcp`):

| Tool | DigitalOcean endpoint(s) | Hints |
|---|---|---|
| `digitalocean_list_droplets` | `GET /v2/droplets` (`tag_name`, `per_page`→`limit`) | readOnly |
| `digitalocean_get_droplet` | `GET /v2/droplets/{id}` | readOnly |
| `digitalocean_create_droplet` | `POST /v2/droplets` | — |
| `digitalocean_delete_droplet` | `DELETE /v2/droplets/{id}` | destructive |
| `digitalocean_droplet_action` | `POST /v2/droplets/{id}/actions` | destructive (covers power/resize/restore types) |
| `digitalocean_list_droplet_actions` | `GET /v2/droplets/{id}/actions` | readOnly |
| `digitalocean_get_action` | `GET /v2/actions/{action_id}` | readOnly, idempotent |
| `digitalocean_list_snapshots` | `GET /v2/droplets/{id}/snapshots` | readOnly |
| `digitalocean_delete_snapshot` | `DELETE /v2/snapshots/{id}` | destructive |
| `digitalocean_list_backups` | `GET /v2/droplets/{id}/backups` | readOnly |
| `digitalocean_list_regions` | `GET /v2/regions` | readOnly |
| `digitalocean_list_sizes` | `GET /v2/sizes` | readOnly |
| `digitalocean_list_images` | `GET /v2/images` (`type` filter: distribution/application/private) | readOnly |

Example — `digitalocean_create_droplet`:

Request (tool args): `{"name": "web-01", "region": "nyc3", "size": "s-1vcpu-1gb", "image": "ubuntu-24-04-x64", "ssh_keys": ["ab:cd:..."], "backups": false, "ipv6": true, "tags": ["prd-21341-test"]}`

Response (tool result, compact JSON, no `indent=2` per SOP A4): `{"id":123456789,"name":"web-01","status":"new","region":"nyc3","size":"s-1vcpu-1gb"}`

Error envelope (all tools, same shape): `{"error":{"code":"not_found","message":"Droplet 123456789 not found","retryable":false}}`

No DB, no migration — this service is stateless and has no datastore of its own. No events/messages produced or consumed. Backward compatibility: this is a first version, nothing to be compatible with; future changes follow SOP §13 (breaking vs. compatible change classification) — see Decisions below for the choices this version itself locks in.

### Key flow / sequence

```
Agent -> Gateway: tools/call digitalocean_create_droplet {args}, header X-DigitalOcean-Api-Token
Gateway -> this service: POST /mcp (same header, Streamable HTTP, no session)
this service -> middleware: header present? no -> 401 (required headers); yes -> set ContextVar
this service -> client.py: POST https://api.digitalocean.com/v2/droplets, Authorization: Bearer <token>
DigitalOcean API -> this service: 202 {droplet:{id,status:"new",...}}
this service -> errors.py: map non-2xx (if any) to the envelope
this service -> Gateway -> Agent: compact JSON tool result
(finally) middleware resets the ContextVar
```

### Non-functional

- Idempotency & concurrency: every tool call opens its own `httpx.AsyncClient` from the request-scoped token (SOP §3.3/§3.4); no module-level or global client holds a credential, so concurrent requests from different tenants cannot see each other's token or in-flight state. `digitalocean_get_action` is naturally idempotent (read-only poll). `digitalocean_droplet_action` is not idempotent by design (DigitalOcean itself queues one action per call) — the tool is not marked `idempotentHint`.
- Performance: Droplets/actions/snapshots/backups lists are capped (`limit` default ≤ 50, hard cap ≤ 200) with `has_more`, per SOP A4 — an account with hundreds of Droplets never returns an unbounded payload. DigitalOcean's own rate limit (5,000 requests/hour/token, documented) is surfaced as `rate_limited` with `Retry-After`, not silently retried past the 120s per-call budget.
- Security: credential only ever read from the `X-DigitalOcean-Api-Token` header (SOP §3.1), never logged, never persisted, never falls back to an environment variable. No real credential is ever committed (`.env`/`.venv` gitignored; `gitleaks detect` run before every merge/release per SOP §11).
- Multi-tenant isolation: tenant boundary is the DigitalOcean API token itself — every call is scoped to whichever account issued the token in that request's header (SOP's "operating model" three laws); the service holds no cross-request state that could leak one tenant's Droplet list into another's response (AC11).
- Observability: structured logs on every tool call (`tool name`, `status`, `duration_ms`, DigitalOcean request id when present) — never the token value. `/health` is a pure local liveness probe (AC12), so an outage on `api.digitalocean.com` is visible as `upstream_error` on actual tool calls, not as a failing health check that would wrongly take the whole service out of rotation.

### Risks & dependencies

- Risk: DigitalOcean's rate limit (5,000 requests/hour per token) could be hit by an agent polling `digitalocean_get_action` too aggressively while waiting for a long-running action (e.g. resize) to complete. Mitigation: `rate_limited` envelope carries `Retry-After`; README documents recommended polling interval.
- Risk: destructive Droplet actions (power_off, resize, restore) can disrupt a running workload if called on the wrong id. Mitigation: every destructive tool requires an explicit numeric Droplet/snapshot id (AC4/AC5/AC7), no name-based or "all" targeting; `destructiveHint` set so calling agents can gate on it.
- Dependency: none on another ticket or repo. `mcp-service-gateway` only needs to route to this connector once it is registered (`/api/vendor-register`) — no gateway code change.
- Dependency: a real DigitalOcean account + API token for the manual lifecycle test pass (dev leg) and for the "needs a real vendor account" test cases below; absence of one does not block merge, INT publish, or registration per SOP.

## Decisions made by DEV01

- Repo/tool scope is Droplets only, not all of DigitalOcean — why: matches the ticket's own framing (Conduit lists Droplets as its own plug-in) and the sibling PRD-21339 (Databases) already being a separate ticket/connector; alternative not chosen: one combined `digitalocean-mcp` for all products, which would also risk exceeding the ≤20-tool cap as more DO resources are added later.
- `digitalocean_droplet_action` consolidates 11 DigitalOcean "droplet action" endpoints into one tool with a `type` parameter, rather than one tool per action — why: SOP A4 says tools are capabilities, not endpoint mirrors, and all 11 share the same request/response shape (`POST .../actions` → action record); alternative not chosen: 11 separate `digitalocean_power_on_droplet`-style tools, which would push the tool count unnecessarily high for no added clarity.
- `rebuild` and `change_kernel` actions are left out of v1 — why: not requested, and `change_kernel` is deprecated by DigitalOcean for most modern Linux images; see Open questions for how to add them later without a contract change.
- Credential header is named `X-DigitalOcean-Api-Token` (not `X-DigitalOcean-Token` or `X-DO-Api-Key`) — why: matches the exact name DigitalOcean's own documentation uses for this credential type ("API token"), reducing ambiguity for whoever fills in the connector's credential field at registration time.
- Pagination default `limit` is 50 (hard cap 200) for all list tools — why: matches the SOP A4 default guidance (`≤ 50` default, `≤ 200` hard cap) uniformly, rather than picking different values per resource type with no evidence any one of them needs a different default.
- Vendor registration name is `digitalocean-droplets` (not `digitalocean`) — why: keeps this connector's identity distinct from the planned `digitalocean-databases` vendor (PRD-21339) so the platform's vendor registry and credential storage never conflate the two products' tokens.

To change any of these, say so in a comment and move the ticket back to 5b - ready for groom.
